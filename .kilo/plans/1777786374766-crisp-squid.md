# OIDC Server Enhancement Plan - Phase 1: Core OAuth

## Overview

Enhance the existing OIDC server with essential OAuth features:
1. **Refresh Token Flow** - Exchange refresh tokens for new access tokens
2. **Token Revocation** - Logout and revoke tokens
3. **PKCE Support** - Secure authorization for public clients (SPAs, mobile)

---

## 1. Refresh Token Flow

### Current State
- Refresh tokens are generated and stored (hashed)
- No endpoint to use them

### Changes

#### `src/routes/oauth.ts` - Modify `POST /o/token`

Add handling for `grant_type=refresh_token`:

```typescript
// In POST /o/token handler
if (grant_type === "refresh_token") {
  const { refresh_token } = req.body;
  
  if (!refresh_token) {
    return res.status(400).json({ error: "invalid_request" });
  }
  
  // Find and validate refresh token
  const hashedToken = hashClientSecret(refresh_token);
  const storedToken = await db.refreshToken.findUnique({
    where: { token: hashedToken },
    include: { user: true, application: true }
  });
  
  if (!storedToken || storedToken.expiresAt < new Date()) {
    return res.status(400).json({ error: "invalid_grant" });
  }
  
  // Generate new access token
  const accessToken = JWT.sign({...}, PRIVATE_KEY, { algorithm: "RS256" });
  
  // Optional: Rotate refresh token
  // Delete old, create new
  
  res.json({
    access_token: accessToken,
    token_type: "Bearer",
    expires_in: 3600
  });
}
```

## 2. Token Revocation Endpoint

### RFC 7009 Compliant

#### `POST /o/revoke`

**Request Body:**
```json
{
  "token": "refresh_token_value",
  "token_type_hint": "refresh_token" // optional
}
```

**Logic:**
1. Validate client credentials (client_id + client_secret)
2. Find token in database
3. Delete/revoke the token
4. Return 200 OK (even if token doesn't exist - for security)

**Implementation:**
```typescript
router.post("/revoke", async (req, res) => {
  const { token, token_type_hint, client_id, client_secret } = req.body;
  
  // Validate client
  const application = await db.oAuthApplication.findUnique({ where: { clientId: client_id } });
  if (!application || !verifyClientSecret(client_secret, application.clientSecret)) {
    return res.status(401).json({ error: "invalid_client" });
  }
  
  // Revoke refresh token
  const hashedToken = hashClientSecret(token);
  await db.refreshToken.deleteMany({
    where: { token: hashedToken, clientId: client_id }
  });
  
  res.status(200).send();
});
```

## 3. PKCE Support (RFC 7636)

### Why PKCE?
Public clients (SPAs, mobile apps) can't securely store client_secret. PKCE prevents authorization code interception attacks.

### Flow:
1. Client generates `code_verifier` (random 43-128 char string)
2. Client computes `code_challenge = BASE64URL(SHA256(code_verifier))`
3. Client sends `code_challenge` with authorization request
4. Server stores challenge with auth code
5. Client sends `code_verifier` with token exchange
6. Server verifies `code_challenge` matches

### Database Changes

#### `src/prisma/schema.prisma` - Update AuthCode model:

```prisma
model AuthCode {
  id                 String   @id @default(uuid())
  code               String   @unique
  clientId           String
  userId             String
  redirectUri        String
  scope              String
  codeChallenge      String?   // NEW: PKCE challenge
  codeChallengeMethod String?  // NEW: "S256" or "plain"
  expiresAt          DateTime
  used               Boolean  @default(false)
  createdAt          DateTime @default(now())

  application OAuthApplication @relation(fields: [clientId], references: [clientId])
  user        User             @relation(fields: [userId], references: [id])

  @@index([code])
  @@index([expiresAt])
  @@map("auth_codes")
}
```

### Utility Functions

#### `src/utils/crypto.ts` - Add PKCE helpers:

```typescript
export function generateCodeVerifier(): string {
  return crypto.randomBytes(32).toString("base64url"); // 43 chars
}

export function computeCodeChallenge(verifier: string): string {
  return crypto.createHash("sha256").update(verifier).digest("base64url");
}
```

### Endpoint Changes

#### `GET /o/authenticate` - Accept PKCE params:

```typescript
const { code_challenge, code_challenge_method } = req.query;

// Store challenge with auth code
await db.authCode.create({
  data: {
    code,
    clientId: client_id,
    userId: user.id,
    redirectUri: redirect_uri,
    scope: scope || "openid",
    codeChallenge: code_challenge as string,      // NEW
    codeChallengeMethod: code_challenge_method || "S256", // NEW
    expiresAt: new Date(Date.now() + 60 * 1000),
  },
});
```

#### `POST /o/token` - Verify PKCE:

```typescript
// For authorization_code grant
if (authCode.codeChallenge) {
  const { code_verifier } = req.body;
  
  if (!code_verifier) {
    return res.status(400).json({ error: "invalid_grant", error_description: "code_verifier required" });
  }
  
  let computedChallenge: string;
  if (authCode.codeChallengeMethod === "S256") {
    computedChallenge = crypto.createHash("sha256").update(code_verifier).digest("base64url");
  } else {
    computedChallenge = code_verifier; // plain
  }
  
  if (computedChallenge !== authCode.codeChallenge) {
    return res.status(400).json({ error: "invalid_grant", error_description: "PKCE verification failed" });
  }
}
```

### 3. PKCE Flow
```bash
# Client generates:
code_verifier="abc123...random"
code_challenge=$(echo -n $code_verifier | sha256sum | base64)

# Authorization request:
GET /o/authenticate?client_id=...&redirect_uri=...&code_challenge=$code_challenge&code_challenge_method=S256

# Token exchange:
POST /o/token with code_verifier
```

---

## Notes

- PKCE is **required** for public clients (no client_secret)
- Authorization Server should support both `S256` and `plain` methods, but `S256` is recommended
- Refresh token rotation is optional but recommended for better security
